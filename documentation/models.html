Models

Model are the core of the MPM simulation. They hold information about the domain (cells, material points), the materials, the sets, etc.

static activeCellsOf(mpmManagers)[source]

The cells that are active in any of the MPM managers.

Cells define no __hash__, so a set of them iterates in an address-dependent order that differs between runs. The order of the active cells fixes their blocks in the system matrix and the order in which their contributions are summed, so the cells are sorted by their unique number.

Parameters:

mpmManagers (list) – The MPM managers.

Returns:

The active cells, each once, sorted by cell number.

_acceptElementStates()

Let every element accept its computed state, across the available threads.

An element’s acceptLastState touches only that element’s own state buffers – for a Marmot element it is the single self._stateVars[:] = self._stateVarsTemp copy – so the elements are independent of one another and this loop parallelizes without any coordination.

It is worth parallelizing because of how the explicit solver uses it, not because of how the implicit ones do. An implicit analysis calls this once per converged increment, amortised over a Newton loop and a linear solve, where 19 ms disappears into the noise. Explicit dynamics calls it on every one of millions of increments: on the anchor pry-out model it was 15.6 % of the whole step, the single largest cost outside the element kernels themselves, and every millisecond of it was serial Python holding 31 of 32 threads idle.

_populateNodeFieldVariablesFromParticleKernelDomains()[source]

Creates FieldVariables on Nodes depending on the all defined particle-kernel interactions. For particles and kernels, the situation is a bit more complicated compared to elements or cells: Unlike for elements or cells, there is no direct connection between a particle and a node. Hence, the fields on the nodes are not necessarily known at the beginning of simulation.

For this reason, we force the user to tell us which particles (which have fields) are interacting with which kernelfunctions during the simulation.

_resizeNodeFieldsForNodes(journal)

Resize the existing NodeFields in place for the current self.nodeSets["all"], instead of rebuilding nodeFields from scratch as _prepareVariablesAndFields() does. Used by mesh mutators (e.g. AMR’s hadaptivity._materialize) so that NodeField identity – and hence any NodeFieldSubset or reference a consumer cached – survives a topology change. ScalarVariables (e.g. Lagrange multipliers of constraints) are rebuilt, but values are preserved by name for constraints that still exist, so their converged state survives the refinement too.

Everything here is recomputed from the current elements, constraints and nodeSets["all"] – the node order of the resized fields is the model’s node creation order, which is why one call after several mutations yields the same layout as one call per mutation. Inside a deferring changes() window the call is therefore only noted, and made once when the window closes.

Parameters:

journal (Journal) – The journal instance.

buildEquationSystem(withSystemMatrix=True)[source]

Lay out the equation system of the model on its active domain; see buildEquationSystem() and MPMEquationSystemLayout.

The active domain consists of the cells that hold material points, the nodes these cells and the particles’ kernel functions reach, and the finite elements and cell elements with their nodes. Its degrees of freedom are numbered on the active nodes; the model’s node sets are located on their nodes in the active domain. The elements the solver computes are the finite elements, the active cells, the cell elements and the particles.

Parameters:

Returns:

updateConnectivity()[source]

Bring the coupling of the degrees of freedom up to date with the converged state, before an increment; see updateConnectivity(). Called by EdelweissFE’s solvers at the start of every increment and of every retry after a cutback.

First the managers assign the material points to the cells they lie in (mpmManagers) and the particles to the kernel functions they reach (particleManagers), each from its converged state: a failed attempt may have left a trial state behind. Then the constraints follow, which couple the nodes the managers have just assigned. Finally, the test functions of the particles are corrected for the new connectivity (vciManagers).

A change of the active domain is a change of the coupling, not of the mesh: no node is created or moved, so the solver rebuilds its equation system, but does not re-equilibrate.

Returns:

True if a coupling changed, so that the equation system has to be rebuilt.

Return type:

bool

writeRestart(restartFile)[source]

Write the converged state of the model to a restart checkpoint: EdelweissFE’s model state (see writeRestart()), and the state of every material point and particle.

The material point method and RKPM are updated-Lagrangian: the material points and particles carry the state, and their positions follow from it. The connectivity – which cells hold which material points, which kernel functions reach which particles, where bonded kernel functions sit – follows from the positions, and is rebuilt by the first connectivity update of the resumed run (updateConnectivity()), as before every increment.

Parameters:

restartFile (File) – An open, writable h5py.File (or group) to write the checkpoint into.

MPMEquationSystemLayout class

What an MPMModel answers EdelweissFE’s implicit solvers (NIST, NISTParallel, NISTPArcLength) when they (re)build their equation system: the active domain, its degrees of freedom and the entities computed like elements, how the solution passes between the model and the solver’s vectors, and the update of the material points before the cells are computed. See EdelweissFE’s documentation, “What the solver asks the model”.

What the equation system of a material point or RKPM model is made of: the answer an MPMModel gives EdelweissFE’s implicit solvers whenever they (re)build their equation system, see buildEquationSystem().

class edelweissmeshfree.models.mpmequationsystemlayout.MPMEquationSystemLayout(model, dofManager, elements, activeCells, nodesWithPersistentFieldValues, activeNodeFields, modelForLinearSolver)[source]

The layout of the equation system of a meshfree model, on its active domain: the background cells that hold material points, the nodes these cells and the particles’ kernel functions reach, and the finite elements with their nodes.

Two kinds of nodes take part. The nodes of finite elements (and of cell elements) carry their total solution from increment to increment, as in a finite element model. The nodes of the grid and of the kernel functions do not: the material point method and RKPM are incremental on the current configuration – the cells are reset after every increment, and the kernel functions move with their particles, while the state lives in the material points and particles. Their nodal values are the coefficients of one increment, and start every rebuilt equation system at zero.

Parameters:

  • model – The model.

  • dofManager (DofManager) – The numbering of the degrees of freedom of the active domain.

  • elements (list) – The finite elements, the active cells, the cell elements and the particles, in the order in which the solver computes them.

  • activeCells (list) – The cells that hold material points, sorted by their number.

  • nodesWithPersistentFieldValues (NodeSet) – The nodes that carry their total solution from increment to increment: those of the finite elements and of the cell elements.

  • activeNodeFields (dict) – The node fields on the nodes of the active domain, which the DOF manager numbers.

  • modelForLinearSolver – The model reduced to its active domain, for the linear solver.
